# OKIT 桌面版 Pro 商业化总体方案

> 状态：方案讨论稿（2026-08-15），待评审后分阶段实施。
> 本文档自包含，供协作方（人类/Agent）无上下文阅读。

## 0. 背景与约束

OKIT 当前形态：本地 CLI + Web Dashboard（`okit web` 起 Express 于 :3780，浏览器访问），管理 AI agent 基础设施——密钥库（vault）、Provider/模型管理、9 个 agent 适配器、15 平台用量查询、auto-create 一键创建密钥的 Chrome 扩展。

关键约束：**直接竞品 cc-switch（127k star）完全免费开源**，provider 切换/模型管理/agent 适配它全有。因此：

- 凡 cc-switch 也有的本地功能，不能收费（收费 = 送用户给竞品）；
- 付费点必须落在 cc-switch 结构性做不了的地方——**有服务端依赖的托管服务**；
- 纯本地功能收不住钱（本地 license 校验可被破解），能收住钱的本质是"服务端可验证的权益"。

## 1. 商业模式：Open Core（Bitwarden 同构）

- **开源版**：保持现状（浏览器启动的本地工具），本地功能永久全量免费，继续承担获客（GitHub star、cc-switch 用户迁移）。
- **桌面 Pro 版**：Electron 打包 + 账号体系 + 支付 + 官方托管服务，卖订阅。
- 边界原则：**功能免费、服务收费**。开源版不阉割任何本地功能（阉割会在免费竞品旁口碑崩盘），包括保留现有 8 个 BYO 同步后端（Cloudflare D1/KV/R2、iCloud、Supabase、WebDAV、火山引擎）作为技术展示。

## 2. 支付与激活

**备案结论**：ICP 备案只约束部署在大陆服务器的网站；收款全部发生在第三方平台页面（LS 结账页/面包多店铺），自有官网不碰交易，无需支付资质。

- **海外：Lemon Squeezy**（首选）。个人可注册、Merchant of Record 代缴全球税务、费率 5%+$0.5。核心优势：**内置 License Key API**——`/v1/licenses/activate`（instance name = 设备标识）、`/v1/licenses/validate`、`/v1/licenses/deactivate`，自带每 license 设备数上限，订阅到期 license 自动失效，支付成功发 webhook。Phase 0 激活服务端几乎不用自研。
- **国内：面包多**（~5%）。自动发激活码。虎皮椒/PayJS 为挂靠灰色模式，不采用。
- **支付形态**：官网 web 页支付（LS 托管结账 / 面包多店铺），桌面端只输激活码——绕开 Mac App Store IAP 强制，国内扫码也顺。
- **本地验证**：激活码 = Ed25519 签名 payload（用户/档位/到期日/设备额度），客户端内置公钥离线验签 + LS 在线激活限设备，双轨。

## 3. 多端同步密钥架构（零知识，方案 B）

设计目标：服务端被拖库也无法解密用户 API key；新设备仅凭账号 + 主密码即可恢复全部数据（无需旧设备在线配对）。

### 密钥体系

```
主密码（仅存在于用户记忆 + 本地内存）
   │
   ├─ KDF(主密码, salt₁) → 登录哈希 auth hash → 发服务端验证（服务端只存它的哈希）
   │
   └─ KDF(主密码, salt₂) → KEK（永不上传）
                                  ┌────────────────────────────┐
   DEK（随机 256-bit，账号级，真正加密 vault 数据） │ 被 KEK 包裹 → wrapped DEK 存云端 │
                                  └────────────────────────────┘
```

- 登录密码与主密码**合一**（同一密码、两条派生路径，HKDF 分叉），用户只记一个。
- 云端存储：auth hash 的哈希、salt₁/salt₂、wrapped DEK、vault 密文——全部非秘密，拖库无泄密。
- **唯一不落云端的输入是主密码**：新设备流程 = 登录 → 拉 salt + wrapped DEK → 本地派生 KEK → 解 DEK → 解密 vault。设备间无需桥梁/配对/推送。
- **改密码 O(1)**：用旧 KEK 解开 DEK，新 KEK 重新包裹，仅上传新 wrapped DEK（几百字节）；数据密文不动不重传。
- **KDF 必须慢速**：Argon2id（首选）或高迭代 PBKDF2（≥600k 迭代），防离线字典攻击；注册强制最低密码强度；UI 明示"密码丢失云端数据无法找回"，并提供一次性恢复码兜底。
- **设备表与加密零耦合**：服务端仅记 `device_id + device_name + refresh_token + last_seen`，用于会话管理与"踢出设备"，不参与任何密码学。
- **迁移**：现有 vault 为 machine-specific 派生（`src/vault/store.ts`）。用户首次开启托管同步时走一次性迁移：设主密码 → 本地机器派生解开 → 改用 DEK 加密上传。⚠️ 实施前需先审计 `cloud-sync-core.js` 现状（当前跨机解密如何处理）。
- 排除项：云端可解密方案（服务商能看明文，密钥库产品硬伤）；设备配对/ECDH 桥梁方案（旧设备不在场即死锁，工程重体验差）。

## 4. 代码组织：单仓 + 目录隔离（禁止双分支）

**不做开源/付费双长期分支**：cherry-pick 漂移 + tag 泄露历史，git 分支不是保密机制。

```
okit/            （公开，唯一 main 分支）
├── src/…        # 开源核心（现状）
├── desktop/     # Pro 桌面版：Electron 壳、账号 UI、激活、托管同步客户端
│                #   构建目标控制：开源构建不编译此目录（物理不进包）
└── …
okit-cloud/      （独立私有仓库，仅本人可见）
└── 账号、支付 webhook、托管同步服务端、告警推送
```

核心认知：**护城河是服务端，不是客户端代码**。`desktop/` 目录公开无妨——没有 okit-cloud 服务端，这些代码跑不起来（Bitwarden 客户端全开源同理）。若仍介意可见性，备选私有 submodule，但 CI/贡献者体验差，不推荐。

## 5. 技术选型与路线图

桌面壳选 **Electron**：`src/web` 为纯 Node CommonJS（Express），Electron 天然带 Node，现有前后端代码近乎 100% 复用；Tauri 需将 Node 后端作 sidecar 打包，成本高，暂不采用。自动更新用 electron-updater（桌面版必须项）。

| 阶段 | 内容 | 服务端工作量 |
|------|------|--------------|
| **Phase 0**（最快见钱） | Electron 壳 + `OKIT_PRO` 构建目标 + 官网支付页（LS/面包多）+ 激活码验证（Ed25519 离线验签 + LS 在线激活）+ electron-updater | 近乎零（LS 承担 license 管理） |
| **Phase 1** | 托管同步 MVP：账号体系、主密码/DEK 密钥体系、vault 加密同步、设备管理 | 重头：okit-cloud 上线 |
| **Phase 2** | 用量告警服务端推送、历史趋势、团队档（密钥分发/聚合/审计） | 扩展 |

### 已识别前置工程

1. 账号/激活体系当前不存在，Phase 0 需从零搭（最小：license key + Ed25519 验签 + 在线激活限次数）。
2. vault machine-specific 派生 → 账号级 DEK 的迁移流程（见 §3）。
3. `desktop/` 构建隔离：`npm run build`（开源）不触碰 desktop；`npm run build:desktop` 打 Electron 包。

## 6. 一句话总结

开源版做到"本地工具的极致"永久免费，桌面版卖的全部是"有服务端的权益"（托管同步 + 用量告警 + 团队管理）；支付走 Lemon Squeezy（海外，license API 免自研）+ 面包多（国内发码）；同步采用零知识主密码架构，服务商技术上无法查看用户密钥；代码单仓目录隔离，私有仅 okit-cloud 服务端。
